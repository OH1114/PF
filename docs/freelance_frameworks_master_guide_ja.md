| 区分 | フレームワーク | 強み（利点） | 注意点（欠点） | 副業案件で多い用途 | 案件単価目安（月） |

## 2. 案件タイプ別の「勝ち筋」

### A. LP + 管理画面（短納期）
- 推奨: Next.js / Nuxt
- 勝ち筋:
  - 最初にデザインシステム（色・タイポ・余白）固定
  - CMS or JSON管理で文言差し替えを簡単に
  - 納品時に「運用手順書」を付ける

### B. AI機能付き業務自動化
- 推奨: FastAPI + Streamlit/Next.js
- 勝ち筋:
  - AIが落ちても動くフォールバック
  - 料金事故を防ぐ上限設定
  - 入出力仕様（CSV/JSON/PDF）を先に合意

### C. 予約・顧客・在庫などの業務システム
- 推奨: Django / Laravel
- 勝ち筋:
  - 権限設計（管理者/担当/閲覧者）を初期設計
  - 監査ログとCSV出力を先に実装
  - 既存運用に合わせた画面遷移優先

### D. API基盤・Bot連携
- 推奨: NestJS / FastAPI
- 勝ち筋:
  - OpenAPI仕様を先に作る
  - エラーレスポンスを統一
  - Webhookの署名検証と再送制御を実装

## 4. `.env` が初めてでも迷わないための基礎

## 4.1 `.env` の役割
- APIキー・DB接続先などの**機密情報をコードから分離**する。
- 本番/開発で値を切り替える。
- Git管理しない（`.gitignore`対象）。

## 4.2 典型例
```env
# アプリ共通
APP_ENV=local
APP_DEBUG=true
PORT=8000

# DB
DATABASE_URL=postgresql://user:password@localhost:5432/appdb

# APIキー
OPENAI_API_KEY=sk-xxxx
LINE_CHANNEL_SECRET=xxxx
LINE_CHANNEL_ACCESS_TOKEN=xxxx
```

## 4.3 実運用ルール
1. `.env.example` に「キー名だけ」を置く（値はダミー）。
2. 実値は `.env` に書き、コミットしない。
3. READMEに「どのキーが必須か」を書く。
4. デプロイ先のSecret Managerにも同じキー名で登録する。

## 5. よくある課題と解消策（副業案件で頻出）

| 課題 | 失敗パターン | 解消の工夫 |
|---|---|---|
| 要件が曖昧 | 開発後に「思ってたのと違う」 | 画面遷移図 + API I/Oサンプルを先に合意 |
| 納期が短い | 作り込みすぎて遅延 | MVP範囲をMust/Should/Wantで分割 |
| API費用が読めない | 想定外課金 | キャッシュ、上限、フォールバック導入 |
| バグ再現しない | 感覚で修正 | ログID、再現手順、テストケース固定 |
| 引き継ぎで詰む | 属人化 | README・ER図・環境変数表を必ず残す |

## 6. 最短効率ロードマップ（8週間）

1. **Week 1-2**: 既存3ポートフォリオを動かし、READMEを読みながら構成を把握。
2. **Week 3-4**: 追加した模擬案件5つのディレクトリを読み、各フレームワークの責務分離を比較。
3. **Week 5-6**: 1つ選んで本当に動く最小実装に拡張（ログイン・CRUD・テスト）。
4. **Week 7**: 仕様書テンプレ（要件/画面/API/テスト）を自作。
5. **Week 8**: 提案文テンプレ + 見積テンプレ + デモ動画を作成。

## 9. 追加PF（09）が他構成と何が違うか

`portfolios/09_saas_monetization_ops_mock` は、既存PFの「機能開発中心」から一段進めて、**売上化と運用**に焦点を当てています。

| 比較対象 | 既存PF（01〜08） | 追加PF（09） |
|---|---|---|
| 主目的 | 画面/API/業務ロジック実装の提示 | Demo版→有料版の収益化導線まで提示 |
| 機能制御 | 実装例が中心 | プラン別機能ゲート（`demo/pro/enterprise`）を明示 |
| 決済連携 | ほぼ未対象 | Stripe前提の課金イベント設計を含む |
| 運用観点 | 開発体験重視 | 課金失敗、監視、障害時運用までカバー |
| 提案時の強み | 技術力の説明 | 「売上に繋がる設計」が説明できる |

## 10. デモ版と有料版にする場合の実装手順（実務向け）

1. プラン定義を固定する  
   - `demo`（機能制限あり、無料）  
   - `pro`（主機能解放、月額）  
   - `enterprise`（追加サポート、個別見積）
2. 機能ゲートをコード化する  
   - 例: エクスポート、API連携、利用回数上限を `featureGate(plan)` で判定。
3. 決済イベントを契約状態へ反映する  
   - `checkout.completed` で `pro` へ昇格。  
   - `invoice.payment_failed` で猶予/制限。  
   - `customer.subscription.deleted` で `demo` に戻す。
4. デモ版のUXを作る  
   - 触って価値が分かる最小機能は開放。  
   - 成果物の一部を意図的に制限し、アップグレード導線を明記。
5. 有料版の利用規約とSLAを準備する  
   - サポート範囲、返信SLA、返金条件、障害時の連絡方法。
6. 本番移行時の運用設定  
   - 監視（Sentry）、分析（GA4/PostHog）、通知（Slack/メール）を有効化。  
   - デモ環境と本番環境でキー・DB・Webhook URLを分離。
